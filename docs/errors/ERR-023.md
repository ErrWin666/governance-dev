# ERR-023 — wsl.exe spawn fails intermittently (0xC0000142) → fail-closed stall

**Type**: environment / transport
**Path**: `%APPDATA%/devin/config.json` hooks → `wsl.exe -d Ubuntu-24.04` →
`policies/gate.sh`
**Discovered**: 2026-11-11 — session teal-income (tools blocked mid-session
with `Command exited with code -1073741502`)
**Status**: Documented — root-cause research complete:
`docs/WSL_SPAWN_RELIABILITY.md`

## Description

The PreToolUse hook spawns a fresh `wsl.exe` per tool call (plus a second
for PostToolUse). Intermittently Windows fails to *create* the process:
exit `-1073741502` = `0xC0000142` STATUS_DLL_INIT_FAILED. `gate.sh` never
runs — `logs/gate.log` contains `PWD-PROOF` entries only for successful
spawns, with silent gaps exactly at the blocked calls. `fail_closed:true`
then converts the transport failure into a hard tool denial.

## Evidence

- Blocked calls left zero trace in `gate.log` — the failure is at Windows
  process creation, before bash/OPA/policy.
- WSL VM cold-booted at 14:58:55 (process start times + `uptime`), and
  Hyper-V `VmSwitch` is rebuilt every ~20–30 min (System log: 12:09,
  12:33, 12:48, 14:30, 14:37, 14:58) — recurring windows where `wsl.exe`
  spawn is fragile. `docker-desktop` distro also running → likely churn
  source.
- Memory pressure: ~2.7 GB free of 16 GB, ~335 processes — 0xC0000142 is
  the classic desktop-heap / resource-pressure spawn failure.
- Amplifier: 2 WSL crossings per tool call × parallel tool calls → bursts
  of 4–6 `wsl.exe`/`wslhost` spawns.

## Root cause (research-backed, docs/WSL_SPAWN_RELIABILITY.md)

Not the policies — when `wsl.exe` spawns, the gate works correctly
(`P13-EXEC-WRITE`, `P13-EXEC-INDIRECTION` denials observed live). Ranked
by the research:

1. **Windows-side spawn failure, not a WSL-VM problem** — `0xC0000142` on
   `wsl.exe` is directly documented (microsoft/WSL#6707, #5448: the code a
   Windows-Terminal dev attributes to "conhost failed to launch"). Under
   ~335 processes / 2.7 GB free, the per-spawn console/DLL init loses an
   allocation race — consistent with "no trace in gate.log".
2. **Architecture amplifies it**: ~2 `wsl.exe` spawns/tool call reaches
   the documented churn volume that wedges WSL session creation
   (WSL#41286: ~80 spawns/22 min → Relay leaks); our 15 s timeout can
   kill `wsl.exe` mid-handshake — the exact trigger that crashes the
   Interop server (codex#46703 → WSL#41592).
3. **VmSwitch rebuild cadence** = idle-VM teardown/recreate loop
   (`vmIdleTimeout` default 60 s; last session exit → VM down → next
   spawn rebuilds NIC). Docker Desktop shares the same utility VM and
   adds "resource saver" churn.

The hook's own timeout can therefore *manufacture* the wedge it keeps
hitting — retries must never kill a mid-handshake `wsl.exe`.

## Interim

- Retry the blocked tool — spawn is transient, retries succeed.
- Hook wrapper that retries `wsl.exe` 2–3× with backoff would absorb the
  blips while preserving fail-closed semantics for real outages.

## Fix candidates (owner deferred 2026-11-11 — "later"; manual retry
suffices for now. Ranked in research doc §5)

1. `vmIdleTimeout=-1` + keepalive anchor session (`wsl -- sleep infinity`
   at logon) — ~30 min, kills the idle-teardown cold-start race.
2. Confirm faulting binary via `Application Popup` Event ID 26 on next
   failure (`wsl.exe` vs `conhost.exe`).
3. Retry wrapper retrying ONLY infra codes (0xC0000142, E_UNEXPECTED,
   0x8007274c) with backoff — never killing mid-handshake.
4. Structural: gate runs fine natively (OPA ships `opa_windows_amd64.exe`;
   Git Bash + `jq.exe`+`python.exe` via winget) — removes the entire
   failure class; `policies/gate.sh.gitbash.bak` shows prior exploration.
5. Alternative structural: `opa run --server` in WSL + loopback HTTP —
   converts 2 process spawns/call into 2 TCP calls.
