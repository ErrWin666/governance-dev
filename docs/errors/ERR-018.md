# ERR-018 — numbers.range descending turns whole command into a segment (P13 false positives)

- **Type**: bug (rego semantics assumption)
- **Discovered**: 2026-11-09, p13 bootstrap session
- **Symptom**: `tail -4 logs/gate.log`, `find policies ...`, `git add policies/`
  all denied by P13 — read-only commands with zero write operators.
- **Root cause**: `some i in numbers.range(1, count(parts) - 1)` — when an op
  does NOT match, `split` returns `[whole]` so `count = 1` and
  `numbers.range(1, 0)` returns `[1, 0]` in OPA (descending ranges are legal
  per spec — verified against OPA builtins.go docs). `i = 0` then leaked
  `parts[0]` = the *entire command* into the protected-path check; any
  protected path mentioned anywhere in the string denied the call.
- **Fix**: iterate `numbers.range(0, count(parts) - 1)` with an `i > 0`
  guard — always-ascending range, index 0 explicitly excluded.
- **Lesson**: substring/pattern policies need negative test vectors as much
  as positive ones. The FP was invisible to `opa check` (syntax-valid) and
  to live deny-tests (they denied anyway). Only a *should-allow* probe
  exposed it — exactly the semantic-regression gap flagged in
  POLICY_COVERAGE item 4. `opa test` files are now mandatory for every
  new/changed policy.
- **Related**: GAP-L1-10 mitigation; industry parallel — Claude Code moved
  command inspection to AST parsing for this class of reason.
