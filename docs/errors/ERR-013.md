# ERR-013 — gitleaks defaults miss alphabet-sequence secrets

- Type: assumption
- Discovered: 2026-11-08, Phase 2 P7 negative test (ci-test PR #4)
- Status: fixed — custom rule in .gitleaks.toml

## Description
The token `sk-abcdefghijklmnopqrstuvwx` committed in a PR was scanned by gitleaks
v8.24.3 default rules and reported "no leaks found". The alphabet-sequence
string is treated as a placeholder, not a credential — the generic-api-key
rule allowlist/heuristics reject it, and no provider rule matches it.

## Root cause
Default scanner rules target real-world key formats and filter out
sequential/placeholder-looking strings to cut false positives. Test secrets
and non-standard token formats fall through the net.

## Fix / Mitigation
.gitleaks.toml in ci-test: [extend] useDefault = true plus a custom rule
openai-style-api-key matching sk-[A-Za-z0-9]{20,}. Workflow pins it via
--config .gitleaks.toml. Verified: PR #4 scan then reported
"leaks found: 1" → check FAIL → ruleset BLOCKED merge (PR #6 retest).

## Lesson
Default secret scanners are not sufficient; coverage is a config surface,
not a binary property. Test the scanner with a deliberately weak secret —
a green first run proves nothing.

## New rule
Rule 30 — any project using gitleaks MUST include project-specific rules
in .gitleaks.toml and prove detection with a negative test before trusting
the check.
